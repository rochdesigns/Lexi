# Money Section Rebuild — Debt-Focus Brainstorm Handoff

> **Status (updated 2026-08-28):** No longer just a brainstorm — the shape below has a written spec with full schema, the backend schema is fully built and merged to `main` (`Account`, `Transaction`, `LedgerService`, and `Debt.linked_account_id` connecting the two halves), and `DebtFocus` now has UI for account management (`/ledger`, step 1) and debt↔account linking (step 3, both from the UI track below). This doc is still a continuity doc, not an implementation plan: for anything not yet built, resume the design conversation or go straight to `superpowers:writing-plans`; don't execute prose against it directly. See "Progress since this handoff" below for what's real vs. still just decided-in-principle.

## Context

The user asked: if the money section of this app were built for public release, how should it work? They explicitly asked to disregard the existing money pages/code/memory for this conversation — this is a from-scratch design exploration, not a critique or continuation of what's already implemented. (The pre-DebtFocus money-section plans/specs this superseded — phase-1 design, credit-card debt/account integration, debt snowball payoff plan, and the envelope budgeting work — have since been deleted from `docs/superpowers/`; the old `/money`+`/debt` code itself is untouched and still live, per the "Resolved" note below.)

Constraints established during the conversation:
- The app will be **free** — no revenue to absorb per-user costs like Plaid.
- The **money section's focus is debt clearing**, not general finance tracking.
- User is **okay with manual entry only for now** (no bank aggregator).

## Decisions reached (in order)

1. **No bank aggregator for now.** Plaid-style aggregators charge per connection and don't work for a free app with no revenue. If live sync is revisited later, SimpleFIN (flat low fee) or GoCardless/Nordigen (EU, free tier) were floated as cheaper alternatives to Plaid. For now: manual entry, with CSV import as a plausible later add-on.

2. **Credit cards are liability accounts.** `is_liability` flips the balance sign convention (purchases increase what's owed). A **payment to a card is a transfer**, not two independent transactions — one linked pair (debit source account, credit card account) — so reports don't double-count it as both an expense and income.

3. **Debt is a first-class domain model**, not just a flagged account. Fields: balance, APR, minimum payment, strategy priority. A payoff engine supports **avalanche** (highest APR first) and **snowball** (lowest balance first) projections. Projections **recompute live off actual balance/payments**, not a fixed amortization schedule set at plan creation.

4. **Revolving vs. installment debt.** Cards still being actively spent on are a distinct "revolving" debt subtype from fixed loans (student loans, car loans), since their balance moves both up (spend) and down (payment) instead of just declining. Spend and payment transactions are tracked separately so the UI can show something like "you paid $200 but spent $150, net progress $50" — visibility into whether active use is undermining the payoff plan.

5. **Budgeting is coupled to the debt engine, not generic.** Zero-based/envelope budgeting per period:
   - Debt minimums are auto-created as non-negotiable envelopes, pulled live from the `Debt` entity (source of truth).
   - Fixed bills funded next.
   - Remaining income allocated to user-defined spending envelopes.
   - Any income left unallocated is suggested (not auto-applied) as an extra payment toward the priority debt.

6. **Underspend sweep is a confirm-tap nudge, not silent auto-sweep.** At period-end, freed/underspent envelope money is offered up ("You freed $47 — send it to [Card X]?") rather than moved automatically, to preserve the user's sense of control over their buffer. This was an explicit tradeoff call: auto-sweep is more motivating but removes the cushion role leftover budget normally plays.

7. **Missed/partial payments trigger re-baselining, not guilt-driven catch-up.** User explicitly confirmed this. When a payment is missed or partial, the payoff projection quietly recalculates off the new actual balance rather than rolling the shortfall into next period's target. Missing the **real minimum** (real-world late fee / credit score risk) is treated as a distinct, more serious case from missing the app's **suggested extra** payment (which only slows payoff — no real-world penalty).

## Progress since this handoff (as of 2026-08-28)

The shape above got a full design pass and the first backend slice is built:

- **Spec written:** `docs/superpowers/specs/2026-08-27-money-section-debt-focus-design.md` turns decisions #1-7 above into prose plus a complete schema — `Account`, `Transaction`, `Debt`, `DebtSettings`, `Bill`/`BillPeriod`, `Envelope`/`EnvelopePeriod`. That resolves the "actual schema" item that used to be open here.
- **A standalone payoff engine and page already existed before this schema pass** (`App\Models\DebtFocus\Debt`/`Settings`, `App\Services\DebtFocus\PayoffEngine`, the `/payoff-plan` page — see `docs/superpowers/specs/2026-08-27-payoff-plan-frontend-design.md`) and predates decision #2's `Account`/`is_liability` model — today's `Debt` has no `linked_account_id`, it's a bare balance/rate/minimum record with no transaction history behind it.
- **The ledger half of the schema is now built too:** `App\Models\DebtFocus\Account` (asset/liability, `is_liability` flips the sign convention) and `App\Models\DebtFocus\Transaction` (income/expense/transfer, a transfer is one row with both legs), plus `App\Services\DebtFocus\LedgerService` (`recordIncome`/`recordExpense`/`recordTransfer`) — the single place that applies the sign-convention rule from decision #2, so a transfer into a liability account correctly decreases what's owed. Commits `41881bb..8e6b212` on `main`. No controller or route calls this yet — it's backend-only, same scoping the payoff engine used.
- **`Debt` is now wired to `Account`:** `Debt.linked_account_id` (nullable FK, `SET NULL` on delete) plus a `Debt::linkedAccount(): BelongsTo<Account>` relation — commit `c7af52d` on `main`, via `docs/superpowers/plans/2026-08-28-debt-linked-account.md`. Still backend-only: nothing sets this field yet, since no controller/UI exposes it (see "Suggested next step" below). Cross-user ownership validation is deliberately deferred to whichever controller change first writes to the field.
- **The ledger has its first UI: `/ledger`, an account management page.** `App\Http\Controllers\LedgerController` (`index`/`storeAccount`/`updateAccount`/`destroyAccount`) and `resources/js/pages/Ledger.vue` — commits `9a5ed5c..7a18ce3` on `main`, via `docs/superpowers/plans/2026-08-28-ledger-accounts-ui.md`. A user can now create/edit/delete `Account` records and see each account's balance plus its 10 most recent transactions (read-only history — no entry yet, that's still step 2 below). Also added: `Transaction::scopeInvolvingAccount()`, a query scope answering "which transactions touch this account" across all three of `Transaction`'s account-referencing columns (`account_id`, `from_account_id`, `to_account_id`) — needed because `Account` has no reverse relation for any of them. Standalone page + sidebar entry, not nested under `/payoff-plan`, per explicit user direction; routes live under `/ledger` specifically to avoid colliding with the old system's `/accounts` path and `AccountController` class name.
  - **How it's used today:** sidebar → Money → Ledger. "Add an account" for name/institution/type/liability-flag/starting balance; click a row to expand its transaction history; pencil/trash icons to edit/delete. There's no way to log a transaction from this UI yet (that's step 2) — the only way to create one today is `LedgerService` from Tinker, same as the manual-verification pattern used for `linked_account_id`.
  - **Known follow-ups surfaced during review, relevant to step 2 below:** `debt_focus_transactions` cascade-deletes on all three account FKs, so deleting one account can silently erase a *surviving* counterpart account's transfer history (the delete-confirm copy now warns about this, but the underlying behavior — probably `nullOnDelete` on the transfer legs plus a "(deleted account)" placeholder — is still an open design call, better made once transaction entry exists and history starts actually mattering). Also: `LedgerController`'s `balance` validation has a `min:0` floor that `LedgerService::applyEffect` doesn't enforce (unreachable today since nothing calls `LedgerService` outside tests, but will matter the moment transaction entry ships and an account can go negative — overdraft or an overpaid credit card). And: editing an account currently overwrites its `balance` directly with no adjustment transaction and the field is still labeled "Starting balance" on both add and edit — fine now, becomes an audit gap once entry exists.
- **Payoff Plan debts are now connected to Ledger accounts (step 3 of the UI track, done as of 2026-08-28).** `PayoffPlanController::linkDebt`/`unlinkDebt` (routes `POST /payoff-plan/debts/{debt}/link` and `/unlink`) let a user pick a liability account from `/ledger` to link to a debt row directly in `PayoffPlan.vue`. Linking requires choosing which side's balance wins (`balance_choice: 'debt'|'account'` — shown as a picker in the UI whenever the two differ at link time) and overwrites the losing side to match; unlinking snapshots the account's current balance back onto the debt so it stays editable. While linked, `/payoff-plan`'s index overrides the debt's `balance` in-memory from `linkedAccount->balance` before running `PayoffEngine`, so the account is the live source of truth without any engine changes — the debt's own `balance` column is only written at link/unlink transitions. Deleting a linked account on `/ledger` now deletes the linked debt too (in the same DB transaction), and the delete-confirm copy names the debt that will go with it. This work is complete and tests pass (12 new Pest tests, `LedgerControllerTest`/`PayoffPlanControllerTest`, 70/70 in the `DebtFocus` suite) but is **uncommitted** — it exists only in the local working tree as of this handoff update, not yet on `main`.
  - **Known follow-up:** the picker only appears when editing an *existing* debt row (linking needs a saved debt id first) — there's no way to link while creating a brand-new debt in the same step. Minor, easy to add later if it turns out to matter.
- **Not yet built:** `DebtSettings` as a shared strategy setting reused by budgeting (today's `Settings` model is payoff-plan-specific), all of `Bill`/`Envelope`/budgeting, manual transaction entry (no UI calls `LedgerService::recordIncome`/`recordExpense`/`recordTransfer` yet), and step 4 below (spend-vs-payment display).
- **Small UX fixes landed on the standalone `/payoff-plan` page** (unrelated to the ledger work above — cosmetic/data-entry fixes on the pre-existing `PayoffEngine`/`DebtFocus\Debt` page): the per-debt interest figure was relabeled "cumulative interest" (it was reading as a monthly amount and caused confusion), and a "Calculate" helper next to the minimum-payment field on revolving debts now suggests `interest + 1% of balance` so users aren't left entering a minimum below what covers accruing interest — this surfaced from a real case (Maya CC's stored minimum payment was $521.09/mo against ~$856/mo of accruing interest, causing several months of negative amortization in the simulation before other debts freed up cash). No schema change; both fixes live in `resources/js/pages/PayoffPlan.vue`.
